# 配置自动升级与恢复

程序读取 `settings.json` 和 `tag_config.json` 时，先检查格式版本，再补齐缺失字段和适配已知旧格式。配置文件新增独立整数标记 `config_schema_version: 1`，不使用应用版本号判断配置格式；标签的 `version: "6.0"` 仍表示原有标签结构版本，数据库版本和数据目录定位版本也分别保持原有含义。

## 自动处理的内容

- 旧扁平 API 设置转成连接档案和任务模型路由，保留原有密钥、地址和模型名。
- 缺失字段补默认值；可确定的数字字符串、`true`/`false` 字符串转成对应类型。保留有效的 `false`、`0`、空列表，以及监控任务的 `null` 继承值。
- 已有路由的空模型保持“继承所选连接的默认模型”，不会因启动而固定成某个模型。仅缺失的旧分析路由槽按原规则初始化。
- 旧标签 `config` 列表迁为 `tag_groups`，保留全局提示词、组提示词、导出配置、分类和扩展字段。已有 `tag_groups` 时以其为准，包括空列表，不从遗留列表重新导入旧词。仍按原规则补齐五个标准组的骨架。
- 连接、模型路由、监控全局与任务中的扩展字段保留；监控任务的身份、启用状态与覆盖关系保留。无法唯一解释的重复连接身份或重复监控目录会停止升级，避免静默合并或丢项。
- 三类 JSON 文件均兼容 UTF-8 BOM。数据目录定位文件只调整读取编码，格式版本及“已初始化目录缺库时报错”的保护不变。

每个发生格式变化的既有设置或标签文件，先将原始字节写入同目录下的 `backups/config-upgrades/`，再原子替换配置文件。备份名为 `原文件名.源内容SHA256.bak`，因此同一内容的失败重试会复用已校验备份。BOM、空白和旧格式均包含在快照中。成功升级后再次启动不会重复改写和生成备份。缺失文件只产生内存默认值，不会仅因读取就创建文件。

## 失败时的行为

配置损坏、重要字段类型错误、未知格式版本或比当前软件更新的标签业务版本，会停止普通加载或拒绝保存，不回退为默认值覆盖原文件。标签业务版本使用版本库比较，因此 `10.0` 会被识别为更新版本。即使程序内存中是旧配置，保存前也会重新检查磁盘格式，避免覆盖另一个版本刚写入的文件。

备份或写入失败会报告失败，原配置和已经完成的备份保留。若写入前发现文件已被其他程序修改，会要求重新加载。该检查和进程内锁用于减少冲突，不提供跨进程事务保证。

设置文件和标签配置分别升级，不能视为一次跨文件事务。某文件升级成功而另一文件失败时，已成功文件保留当前格式，失败文件保留原样；修正原因后重新启动可继续。自动保存失败时保留界面编辑内容，可重试；错误文案不回显密钥或配置原值。

已有标签导入恢复记录是例外：数据库已经提交，标签文件只是其投影，可以按原恢复协议重建损坏投影。重建前也保留源字节，并且同样拒绝覆盖未来版本文件，恢复记录在写入成功后才删除。

## 如何恢复

1. 退出程序，保留当前配置和 `backups/config-upgrades/`。
2. 找到所需文件对应的 `.bak`，复制为原文件名放回原目录。备份是原始文件内容，无须解压。
3. 再次使用支持该格式的软件启动；若恢复的是旧配置，本版会重新进行适配。未来版本配置应使用相应更新版本的软件，不要手改版本号强制降级。

快照可能包含 API Key、服务地址和自定义提示词，需与原配置同样妥善保管，不应上传或加入 Git。这里的文件快照只用于配置恢复，不能替代“数据与维护”中的完整管理数据备份，也不能回滚数据库。

配置升级不会移动数据目录、迁移数据库、导入旧分析结果或改变软件版本号。这些操作仍保留原有确认和恢复流程。
