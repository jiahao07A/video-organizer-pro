# Subagent 调用规范

Status: adopted

本文规定主 Agent 如何判断是否调用 Subagent、调用前必须准备什么、如何编写执行指令，以及如何审查和接收 Subagent 的结果。

这里的“主 Agent”是当前直接负责用户请求、范围判断、方案决策和最终交付的 Agent；“Subagent”是由主 Agent 委派来完成一个受限子任务的 Agent。Subagent 是执行协作者，不是新的需求分析者，也不拥有本任务的最终决策权。

本文件补充以下规范：

- [Git 与 GitHub 工作流及工作标准](./git-github-workflow.md)
- [本地 Markdown 议题追踪](./issue-tracker.md)
- [领域文档规则](./domain.md)
- 根目录 `AGENTS.md`

## 1. 强制底线

### 1.1 搜索类任务是唯一的提前委派例外

除搜索类任务外，主 Agent 必须先自行获取足够完整的信息，再调用 Subagent。适用范围包括但不限于：

- 增加功能或改变现有行为；
- 新的开发任务；
- bug 诊断、debug 和 fix；
- 重构、性能优化、依赖或构建改动；
- 编写或修改测试；
- 编写或修改项目规范、Issue/PR 模板和 `docs/` 文档；
- 代码审查、安全审查、迁移和发布准备。

主 Agent 必须先完成：

1. 读取用户需求、相关 Issue、`.scratch/` spec/子议题和工作区状态；
2. 阅读相关 `CONTEXT.md`、ADR、Agent 文档和现有实现；
3. 确认当前行为、问题边界、依赖、约束和已有决策；
4. 对 bug 或 debug 任务取得足以支持判断的复现、日志、测试或代码证据；
5. 判断任务应当打包还是拆分，明确本次范围内与范围外；
6. 做出本轮所需的产品、架构、接口、数据和实现决策；
7. 写出可执行的实施方案、验收标准、验证命令和风险/回滚方式。

然后，主 Agent 才能把完整执行方案交给 Subagent。指令必须让 Subagent 可以直接开始修改或验证，不得只转发用户原话，也不得要求 Subagent“先研究一下再决定怎么改”。

如果主 Agent 还无法说明应该改什么、为什么这样改、改动不能越过哪些边界，就说明信息或决策尚未完成，不能调用 Subagent 执行该任务。

### 1.2 搜索类任务的边界

搜索类任务只产生信息、证据或文件定位，不直接修改项目。典型例子：

- 查找某个符号、调用链、配置项或测试位置；
- 在指定目录中查找某个行为、错误消息或文档规则；
- 汇总已有实现、相关 ADR 或现有议题；
- 对代码库进行有明确问题的定向探索。

搜索任务也必须有明确的搜索问题、仓库/目录范围、关键词或符号、期望输出和禁止事项。搜索类任务完成后，主 Agent 仍必须自行理解结果并形成方案；不能因为 Subagent 找到了文件，就直接让它继续修改而跳过主 Agent 的分析门槛。

如果一次委派同时包含“搜索并修改”“研究并实现”“诊断并修复”，整体按非搜索类任务处理，必须先完成完整方案。

## 2. 何时调用 Subagent

### 2.1 适合调用的情况

满足以下条件时，可以调用 Subagent：

- 子任务边界清楚，可以用文件、符号、目录、测试或输出物明确限定；
- 主 Agent 已完成必要调查和方案决策；
- 子任务可以独立执行、验证或产生有价值的搜索结果；
- 委派可以明显减少总耗时、降低遗漏，或需要另一轮独立审查；
- 主 Agent 能够在返回后检查差异和验证结果。

适合委派的执行任务包括：

- 按已确定方案修改一个明确模块；
- 为已确定的行为补充测试；
- 在不改变方案的前提下完成文档、模板或样例更新；
- 针对明确复现步骤实施已确定的 bug 修复；
- 对一个已经限定的文件集合进行格式、链接或一致性检查；
- 对已确定范围进行独立代码审查或安全检查。

### 2.2 不应调用的情况

出现以下情况时，不应调用 Subagent 执行修改：

- 需求、范围、验收或优先级仍然模糊；
- 需要用户在多个产品或架构方案中做选择；
- 主 Agent 尚未读取相关代码、文档、ADR 或测试；
- bug 尚未复现，也没有足够证据支持修复方向；
- 子任务会同时跨越多个未决策的模块；
- 修改可能影响数据迁移、原始素材、凭据、发布分支或其他高风险对象，但备份和回滚方案未确定；
- 任务只有一两个直接工具调用即可完成，委派成本高于执行收益；
- Subagent 的结果无法被主 Agent 复核；
- 需要 Subagent 替主 Agent 规划整个用户请求。

可以先调用 Subagent 做定向搜索，但不能把“先让 Subagent 看看该怎么做”当成非搜索任务的执行前置阶段。

## 3. 调用前的准备包

非搜索类任务调用前，主 Agent 必须准备一份“执行包”。执行包可以放在调用指令中，也可以先写入 `.scratch/` 议题或 PR 记录，但必须在 Subagent 指令中完整引用关键内容。

执行包至少包含以下内容：

### 3.1 任务身份

- 任务目标和用户可见结果；
- GitHub Issue、`.scratch/` spec/子议题和当前分支；
- 本次子任务与父任务的关系；
- 是否允许修改、只读检查或只输出建议。

### 3.2 已确认的现状

- 当前相关行为和代码路径；
- 已阅读的文件、类、函数、配置和测试；
- 已确认的约束、已有 ADR 和领域术语；
- bug 的复现步骤、日志、失败测试或其他证据；
- 当前工作区中与本任务无关、禁止触碰的改动。

### 3.3 已决定的方案

- 要采用的具体行为和实现方式；
- 要修改的文件、模块、类、函数或文档章节；
- 数据结构、接口、线程、错误处理、兼容性或迁移决定；
- 不采用的方案及原因（如果这能防止 Subagent 重新做决策）；
- 明确禁止改变的行为。

### 3.4 执行步骤

执行步骤必须具体到足以直接操作，例如：

1. 在 `core/example.py` 的 `ExampleService.run()` 增加什么边界处理；
2. 在 `tests/test_example.py` 增加哪些输入和预期；
3. 更新 `docs/example.md` 的哪一节；
4. 运行哪些命令；
5. 返回哪些结果和剩余风险。

不能只写“优化服务层”“修复相关问题”“补充测试”或“按最佳实践重构”。

### 3.5 验收、风险与回滚

- 必须通过的行为验收标准；
- 必须运行的测试、静态检查、构建或人工步骤；
- 不允许降低或删除的既有测试；
- 可能影响的文件、数据、配置或外部服务；
- 失败时的停止条件；
- 回滚方式和不可恢复边界。

## 4. 如何编写 Subagent 指令

### 4.1 通用指令结构

Subagent 指令应使用简体中文优先，并采用以下顺序：

```text
你是本任务的执行 Subagent。请严格按下面已经确定的方案执行，不要重新规划范围、架构或产品行为。

## 任务目标
<完成后的明确结果>

## 已确认现状
<代码、文档、测试、复现证据和约束>

## 本次范围
<允许修改的文件/符号/文档章节>

## 明确方案
<逐条写出要如何修改，以及不能改变什么>

## 执行步骤
1. <具体步骤>
2. <具体步骤>

## 验收与验证
<命令、测试、人工检查和预期结果>

## 禁止事项
<禁止扩大范围、禁止修改的文件、禁止引入的行为>

## 返回格式
<要求汇报修改文件、验证结果、风险和未完成项>
```

命令、路径、分支名、Issue 标签、代码符号、错误消息和测试名称保持原格式；解释和说明优先使用简体中文。

### 4.2 执行类指令的最低要求

调用新增功能、开发、debug、fix、重构、测试或文档执行 Subagent 时，指令必须明确：

- “按方案执行”，而不是“请分析并决定方案”；
- 要改的具体文件和符号；
- 每个修改的预期行为；
- 需要保留的现有行为和边界；
- 必须运行的验证命令；
- 完成条件、停止条件和返回格式。

如果方案中仍存在未决策项，应由主 Agent 先处理，或把该部分明确标为“只调查、不修改”。不能把未决策项藏在执行指令中交给 Subagent 自由选择。

### 4.3 搜索类指令的最低要求

搜索类指令至少明确：

- 要回答的一个或多个问题；
- 搜索的仓库、目录、文件类型或提交范围；
- 关键词、符号、错误消息或行为描述；
- 需要返回的文件路径、行号、调用关系、证据摘要或不确定性；
- 禁止修改文件、运行破坏性命令或扩大搜索范围（如适用）。

搜索结果应区分“直接证据”“合理推断”和“未找到/未验证”，避免把搜索排序结果当作完整调用图或最终结论。

## 5. 多个 Subagent 的并行调用

只有在子任务彼此独立时才并行调用。并行前必须确认：

- 子任务的文件集合不重叠，或明确为只读任务；
- 一个子任务的结果不会改变另一个子任务的执行前提；
- 每个子任务都有独立的指令、验收和返回格式；
- 主 Agent 能够分别审查每个结果。

禁止让多个 Subagent 同时修改同一个文件、同一组测试或同一个数据迁移边界。需要先后依赖时，按顺序调用，并在后一个指令中提供前一个结果。

并行搜索可以用于互相独立的文件/模块调查，但汇总、取舍和最终方案仍由主 Agent 负责。并行执行修改时，应优先拆成互不冲突的文件范围；无法安全隔离时改为串行。

## 6. 分支、工作区和提交要求

- Subagent 必须遵守本仓库的分支规则，不能直接在 `main` 上开发或提交。
- 主 Agent 应在调用前确定 Subagent 使用的分支、工作树或只读工作区，以及允许触碰的文件范围。
- 默认不要让 Subagent 自动提交。除非指令明确要求，否则由主 Agent 在审查差异和验证结果后提交。
- 如果确实要求 Subagent 提交，必须同时指定提交范围、提交消息、验证要求和是否允许追加修正提交；Subagent 不能提交执行包范围之外的文件。
- Subagent 不得清理、重置、覆盖或删除主 Agent 或用户已有的无关改动。
- Subagent 不得提交 API Key、个人配置、本地数据库、运行日志、真实视频、缩略图、构建产物或其他敏感/生成文件。
- 发现范围不足、方案矛盾、工作区冲突、权限问题或验证无法完成时，应停止修改并报告，不应自行扩大范围或猜测解决。

## 7. 主 Agent 的结果审查责任

Subagent 返回“完成”不等于任务完成。主 Agent 必须独立完成以下步骤：

1. 检查 Subagent 修改的文件和差异，确认没有越过执行包范围；
2. 对照已确认方案检查行为、接口、数据、线程和错误处理；
3. 检查是否误改用户已有内容、敏感配置、生成产物或无关文件；
4. 运行规定的测试、静态检查、构建或人工验收；
5. 对失败、跳过、环境限制和未验证项作出明确记录；
6. 必要时要求 Subagent 按具体反馈补充修改，不能让它自行重新设计；
7. 将结果同步到 GitHub Issue、PR 和 `.scratch/` 记录；
8. 由主 Agent 决定是否提交、创建 PR、合并或回滚。

主 Agent 不能只根据 Subagent 的文字总结判断正确性，必须以实际差异和验证证据为准。Subagent 的搜索结果、诊断结论和测试结果都属于待审证据，除非主 Agent 已复核，否则不能直接作为最终事实。

## 8. Subagent 返回格式

除非任务另有约定，Subagent 完成后应按以下格式返回：

```text
## 结果
- 完成/部分完成/阻塞：<状态>
- 对照执行包的完成情况：<逐项说明>

## 修改或搜索范围
- 文件、符号、文档章节或搜索目录：<列表>
- 未触碰的明确禁止范围：<如有>

## 验证
- 命令：`<完整命令>`
- 结果：<通过/失败/未运行>
- 关键输出：<简要摘要>

## 风险与未完成项
- <事实、限制或未验证部分>

## 下一步
- <主 Agent 需要审查、补充或决定的事项>
```

如果 Subagent 没有修改文件，也必须说明实际搜索了什么、找到什么、没有找到什么，以及哪些结论仍未验证。

## 9. 与 GitHub Issue、PR 和 Debug 的衔接

- 委派前：在 Issue 或 `.scratch/` 记录范围、执行包、Subagent 角色和预期输出；敏感信息不得写入。
- 委派中：重要阻塞、范围变化和方案决定追加到 Issue 评论，不通过私下对话替代记录。
- 委派后：记录 Subagent 实际修改、验证命令、失败项、主 Agent 的复核结果和下一步。
- PR 中：说明哪些修改由 Subagent 执行、主 Agent 如何审查，以及测试和人工验收证据；不把“Subagent 已完成”当作验证结论。
- Debug 中：可以把 Subagent 的搜索或复现结果作为证据来源，但必须注明证据是否由主 Agent 复核；最终修复仍按 Issue、分支、commit 和 PR 规范执行。
- Subagent 发现的超范围问题应创建新 Issue 或追加到已有 Issue 的“后续工作”，不能顺手混入当前 PR。

## 10. 调用前检查清单

### 搜索类任务

- [ ] 搜索问题已经明确。
- [ ] 搜索范围、关键词/符号和输出格式已经明确。
- [ ] 已明确只搜索、不修改，或明确允许的最小只读操作。
- [ ] 已说明如何区分证据、推断和未验证结果。

### 非搜索类任务

- [ ] 主 Agent 已读取相关 Issue、spec、代码、测试、`CONTEXT.md` 和 ADR。
- [ ] 已完成现状调查，bug 已有复现或足够诊断证据。
- [ ] 已明确目标、范围内、范围外和禁止修改的内容。
- [ ] 已完成产品、架构、接口和数据等必要决策。
- [ ] 已列出具体文件、符号、修改行为和执行步骤。
- [ ] 已确定测试、验收、风险和回滚方式。
- [ ] 已确定分支/工作树、提交责任和工作区边界。
- [ ] 已准备好完整执行指令，而不是把规划任务交给 Subagent。

### 返回后

- [ ] 已检查实际差异和文件范围。
- [ ] 已独立运行或复核必要验证。
- [ ] 已记录失败、跳过、风险和未验证项。
- [ ] 已同步 Issue、PR 和 `.scratch/` 记录。
- [ ] 主 Agent 已决定是否提交、创建 PR、合并或回滚。
