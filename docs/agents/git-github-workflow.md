# Git 与 GitHub 工作流及工作标准

Status: adopted

本文件规定本仓库从需求进入、范围确认、分支开发、提交、Pull Request（PR，拉取请求）、合并到问题追踪与故障回溯的统一做法。它补充而不替代以下现有约定：

- [本地问题追踪约定](./issue-tracker.md)：`.scratch/` 中的 spec、议题文件、状态行和评论追加方式。
- [Triage 标签](./triage-labels.md)：议题处理阶段使用的五个规范标签。
- [项目领域词汇](../../CONTEXT.md)：产品和技术文档中必须使用的业务术语。
- `docs/adr/`：已经接受的架构决策。新方案若改变已有决策，必须先提出新的决策记录或明确说明取代关系。

### 1.1 语言标准

- GitHub Issue 的标题与正文、Issue 评论、PR 标题与正文、`.scratch/` 规格记录，以及今后新增或大幅修改的 `docs/` 文档，统一以**简体中文为优先语言**。
- 英文可以作为参照，但应放在中文内容之后或单独的 `English reference` 区块中；中英文不一致时，以简体中文为准。
- 技术标识保留原格式，不强制翻译：GitHub 标签名、Conventional Commits 的 `type`、分支名、命令、文件路径、代码符号、API 名称和原始错误消息可以使用英文。必要时用中文解释其含义。
- 新文档首次出现专业术语时，可以在中文后用括号补充英文，例如“拉取请求（Pull Request，PR）”。不应为了英文参照重复整篇内容。
- 历史文档、历史 Issue、历史评论和已有提交消息不因本规则而改写。今后修改这些内容时，新增说明仍使用简体中文优先。

## 1. 核心原则

1. **先定义范围，再开发。** 任何开发、修 bug、重构、性能优化、配置/依赖调整和流程文档变更，都要先写清楚目标、边界和验收方式。用户没有主动要求范围说明时，也由执行者先补齐。
2. **主干只保存可集成成果。** `main` 是受保护的集成分支，禁止直接在 `main` 上开发、修改或提交。所有改动都从独立分支进入 PR。
3. **提交是可回退的检查点。** 每个 commit 应代表一个有明确意图、能单独解释和尽量能单独验证的变更单元。提交频率以降低回退成本为准，不以“全部做完后一次提交”为准。
4. **PR 是合并边界。** 分支完成后必须创建 PR，通过审阅和验证后再合并；不得用本地 `git merge` 直接把分支合入 `main`。
5. **Issue 是任务的可追踪身份。** GitHub Issue（议题）负责共享任务状态、讨论、决定和验收；仓库中的 `.scratch/` 负责详细规格、执行拆分和接手信息。两者互相链接，不制造互相矛盾的第二套事实。
6. **证据优先。** Issue、commit、PR 和调试记录应包含可复核的命令、测试、日志摘要、环境和已知限制；不得把猜测写成已验证结论。
7. **保护敏感数据和原始素材。** API Key、个人配置、本地数据库、日志中的敏感内容、真实视频素材和生成产物不得进入 commit、Issue、PR 描述或截图。

## 2. 开发前的范围门槛

### 2.1 先判断是打包还是拆分

把一系列小动作放在同一范围内，必须同时满足：

- 共同服务于一个用户结果或一个明确的维护目标；
- 使用同一套验收标准；
- 具有相同的风险、回滚方式和评审人；
- 可以在一个分支和一个 PR 中完整说明；
- 中途失败时不会阻塞其他本来可以独立交付的功能。

出现以下任一情况，就按功能、需求、风险或作用范围拆成多个子任务、分支和 PR：

- 用户结果不同，或验收标准不同；
- 数据迁移、文件变更、外部 API、权限/安全、性能等风险不同；
- 回滚方式不同；
- 需要不同的评审人或不同的交付时机；
- 需要先后依赖，某一部分可以单独验证；
- 修改范围已经难以在一个 PR 中逐项说明。

大任务用一个父 Issue 说明整体目标，再建立编号明确的子 Issue。子任务应按可验证的垂直能力拆分，而不是简单按“改哪个文件”拆分。例如先拆成“建立数据接口”“接入界面”“补充验收”，而不是把同一功能按文件夹切开。

### 2.2 范围记录的最低内容

开始编码前，必须在 GitHub Issue 和对应的本地 spec/议题记录中写明：

- **背景和问题**：当前行为、实际影响、为什么现在处理；
- **目标**：完成后用户或维护者能做什么；
- **范围内**：本轮明确要改变的行为、文件/模块或文档；
- **范围外**：明确不处理的相关问题，防止开发过程中无声扩大；
- **验收标准**：可观察、可执行、可判断通过或不通过的条目；
- **依赖和约束**：相关 Issue、ADR、API、平台、数据格式或人工验收；
- **风险与回滚**：可能损坏什么、如何验证、如何恢复；
- **验证计划**：要运行的测试、静态检查、人工操作或样本范围。

范围未明确时，议题应使用 `needs-info`；信息齐全且可以开始实现时，使用 `ready-for-agent`。需要维护者或用户亲自处理而不是交给代理实现时，使用 `ready-for-human`。

### 2.3 开发前检查现状

执行者应先读取相关领域文档、ADR、现有 Issue/本地议题和工作区状态。至少确认：

```powershell
git status --short --branch
git log --oneline --decorate -12
git fetch origin
```

发现工作区已经有与本任务无关的修改或未跟踪文件时，不得顺手加入本次提交，也不得覆盖、清理或重置它们。应在本地记录这些文件，必要时先向用户说明。只有确认它们属于本任务，才能加入范围。

## 3. GitHub Issue 规范

### 3.1 什么时候必须创建 Issue

以下工作必须有 GitHub Issue；同一目标的一组小任务可以共用一个 Issue：

- 新功能、用户可见行为改变和产品规则改变；
- bug、回归、数据错误、崩溃、性能退化和兼容性问题；
- 数据结构、迁移、导入导出或文件操作变更；
- 依赖、构建、发布、CI（持续集成）、安全或权限变更；
- 会影响其他协作者、长期维护或后续排错的重构；
- 修改团队 Git/GitHub 工作方式的规范、模板和文档。

以下情况可以不单独创建 Issue，但必须并入一个已有的、范围相同的 Issue 或在 PR 中说明：纯拼写修正、同一文档内的排版修复、不会改变行为的局部格式化，以及一次性本地实验。实验一旦准备进入仓库，就必须转为有范围和验收标准的 Issue。

### 3.2 标题和类型

标题应让未看正文的人知道“要解决什么”和“影响哪里”。建议使用以下前缀，并保持标题简短：

- `[Bug] ...`：当前行为错误、崩溃、回归或数据问题；
- `[Feature] ...`：新增用户能力或产品行为；
- `[Task] ...`：重构、性能、依赖、构建、测试或维护任务；
- `[Docs] ...`：规范、说明和架构文档变更。

标题描述问题或结果，不写实现方案作为唯一标题。例如使用“`[Bug] 分析失败后行状态显示为成功`”，而不是“`[Bug] 修改 analysis_worker.py`”。标题和正文优先使用简体中文；`[Bug]`、`[Feature]`、`[Task]`、`[Docs]` 这类类型前缀可以保留为统一的英文标识。需要国际协作时，可在正文末尾增加英文参照，但中文内容是权威版本。

每个 Issue 初始至少使用一个规范 triage 标签，五个标签的含义见 [`triage-labels.md`](./triage-labels.md)：

- `needs-triage`：刚提交，尚未完成范围判断；
- `needs-info`：等待复现信息、产品决定或其他输入；
- `ready-for-agent`：范围和验收已明确，可以由代理或开发者实现；
- `ready-for-human`：需要人工决定、操作或实现；
- `wontfix`：明确不处理，关闭前必须说明原因。

可以追加项目现有的类型、领域、优先级标签，但不能用自定义标签替代上述五个规范 triage 标签。一个 Issue 同一时间只保留一个 triage 标签。

### 3.3 Issue 正文要求

Bug Issue 至少提供：

- 可复现的现象和影响范围；
- 最小复现步骤、输入条件和期望/实际结果；
- 首次发现时间，若已知则提供最后正常版本、首个异常 commit 或 PR；
- 运行环境、应用版本、配置前提和脱敏日志；
- 是否有临时规避方法；
- 修复后的验收标准和回归验证范围。

Feature/Task/Docs Issue 至少提供：

- 背景、目标和目标用户/维护者；
- 范围内与范围外；
- 验收标准；
- 依赖、风险和回滚方式；
- 需要更新的文档、测试、迁移或发布说明；
- 相关 `.scratch/`、ADR、Issue、PR 或外部资料链接。

模板位于 `.github/ISSUE_TEMPLATE/`。如果信息还不完整，应先补问题和评论，而不是让实现者从模糊描述中猜范围。

### 3.4 Issue 评论规范

Issue 评论是追加式记录，不删除或改写已经作出的决定来掩盖历史。每次有影响范围、方案、依赖、验收或状态的变化，都追加一条评论，使用清晰的开头，例如：

- `状态更新`：当前完成了什么、下一步是什么、是否阻塞；
- `范围决定`：纳入/排除什么，以及原因；
- `方案决定`：选择了什么、否决了什么、为什么；
- `验证记录`：命令、样本、结果和未验证部分；
- `问题`：等待谁提供什么信息；
- `交接`：当前分支、最后 commit、剩余工作和风险。

评论应说明事实和证据，不把“应该可以”写成“已通过”。讨论完成后，用一条总结评论固定最终决定，并把对应的验收或范围同步回 Issue 正文、本地 spec 和 PR。关闭 Issue 时，追加关闭总结，包含：关联 PR、合并 commit、验收结果、遗留风险和后续 Issue。

## 4. 分支规范

### 4.1 主干和分支关系

- `main` 是受保护主干，只接受 PR 合并。
- 每个独立范围至少新建一个分支；不能在 `main` 上直接开发、修改或提交。
- 一个分支只对应一个 Issue 或一个已明确打包的范围；不得把无关 bug、格式化和功能混在一起。
- 长期任务用子任务分支分别实现；只有在确有需要时才创建集成分支，集成分支仍必须通过 PR 合入 `main`。
- 紧急修复也要走 `hotfix/` 分支和 PR。紧急只允许缩短评审和验证，不允许把修改直接提交到 `main`。

### 4.2 分支命名

分支名使用小写、短横线和稳定的 Issue 编号：

```text
feat/<issue-number>-<short-slug>
fix/<issue-number>-<short-slug>
refactor/<issue-number>-<short-slug>
perf/<issue-number>-<short-slug>
test/<issue-number>-<short-slug>
docs/<issue-number>-<short-slug>
chore/<issue-number>-<short-slug>
hotfix/<issue-number>-<short-slug>
```

`<short-slug>` 只表达范围，不写个人姓名、日期或临时情绪。没有 GitHub Issue 编号的仓库初始化/规范引导任务可以暂时使用 `docs/<short-slug>`，但在第一次推送前必须补建 Issue 并在分支、PR 或本地 spec 中互相链接。

从最新主干创建分支的标准步骤是：

```powershell
git status --short --branch
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feat/123-short-slug
```

若本地存在未提交改动，不得为了更新主干而使用 `reset --hard` 或覆盖它们。先区分本任务改动和其他改动，再选择提交、暂存、单独保存或请求用户决定。

### 4.3 开发中同步主干

在 PR 进入最终审阅前，应把分支同步到最新 `origin/main`，并重新运行验证。分支尚未被他人使用时，优先使用 rebase；分支已被共享或正在审阅时，不改写他人已经基于其创建的 commit，改用合并主干并在 PR 中说明冲突处理。

```powershell
git fetch origin
git rebase origin/main
# 或：git merge origin/main
# 解决冲突后重新运行完整验证
git push --force-with-lease   # 仅限已说明且无人基于该分支继续开发的 rebase
```

## 5. Commit 规范

### 5.1 Commit 的目标

Commit 是回退、审阅、定位回归和 `git bisect`（二分查找异常提交）的基本检查点。每个 commit 应做到：

- 只有一个主要意图；
- 不包含无关格式化、临时调试、个人配置或生成产物；
- 能说明为什么改、改了什么、如何验证；
- 在合理条件下可以单独编译、运行或通过相关测试；
- 不把半完成的危险迁移与无关功能放进同一个不可分割的大提交。

提交过少会让回退范围过大；提交过多而每个只改一行、无法解释或无法验证，会增加审阅噪声。标准不是固定“每多少分钟一个 commit”，而是每完成一个可解释的恢复点就提交一次。

### 5.2 建议的提交时机

应当在以下时机提交：

- 范围内的一个独立逻辑单元完成，并通过针对性验证；
- 测试、文档、迁移或配置已经形成可独立审阅的配套单元；
- 开始高风险操作前，先保存一个已验证的安全基线；
- 完成风险操作后，验证通过再保存结果；
- 需要切换任务、交接、暂停或长时间离开前；
- 修复一个回归后，先提交最小修复，再提交必要的补充测试或文档。

可以在本地使用 `wip` 或 `fixup` 作为临时检查点，但它们不得未经整理直接作为最终 PR 的核心历史。分支已经推送并被审阅后，优先追加修正 commit；只有确认没有其他人基于该分支工作时，才可在 PR 早期用 `--force-with-lease` 整理历史。

### 5.3 提交消息格式

采用 Conventional Commits（约定式提交）格式：

```text
<type>(<scope>): <imperative summary>

<body: why / important behavior / migration notes>

Refs #123
```

常用 `type`：

- `feat`：新增能力；
- `fix`：修复错误或回归；
- `refactor`：不改变外部行为的结构调整；
- `perf`：性能改进；
- `test`：测试新增或修改；
- `docs`：文档和规范；
- `chore`：构建、依赖、工具或维护；
- `build`：构建/打包系统；
- `ci`：持续集成配置；
- `revert`：撤销已有提交。

`scope` 使用稳定模块或能力名，例如 `gui`、`analysis`、`tags`、`docs`、`build`。摘要使用动词开头，说明结果而不是编辑动作。破坏性变更必须在正文写明 `BREAKING CHANGE:`，并列出迁移和回滚步骤。

提交前至少执行：

```powershell
git diff --check
git status --short
git diff --staged --stat
# 按本次范围运行相关测试、静态检查或人工验收
```

### 5.4 提交内容边界

禁止提交：

- API Key、密码、个人访问令牌、真实服务配置；
- 本机数据库、运行日志、真实视频、缩略图和临时输出；
- 未经说明的构建产物和压缩包；
- 与当前 Issue 无关的用户本地修改；
- 通过删除测试、放宽断言或屏蔽错误来制造“通过”的修改。

误提交敏感信息时，应立即停止继续传播，撤销凭据并按安全事件流程处理；仅删除文件再提交不能证明敏感信息已经从历史中移除。

## 6. Pull Request 规范

### 6.1 什么时候创建 PR

一个分支在范围内的实现、测试/人工验收、文档更新和风险说明完成后，创建 PR。开发中可以先创建 Draft PR（草稿 PR）展示进展，但必须标明未完成项；未完成的 PR 不能被当作可合并结果。

一个 PR 默认只服务一个 Issue 或一个已经在范围记录中批准的任务包。大型任务拆成多个 PR 时，每个 PR 都要说明依赖顺序和独立验收方式。

### 6.2 PR 标题和正文

PR 标题沿用 Conventional Commits，例如：

```text
docs(workflow): 制定 Git 与 GitHub 工作规范
```

PR 标题和正文优先使用简体中文。Conventional Commits 的 `type`、`scope` 和关联关键字（例如 `Fixes #123`、`Refs #123`）可以保留英文；应在中文正文中说明改动内容。需要国际协作时，可在正文末尾增加英文参照，但中文内容是评审和验收依据。

正文必须包含：

- 改动摘要和用户/维护者可见结果；
- `Fixes #123` 或 `Refs #123` 等 Issue 关联；
- 范围内、范围外和主要设计决定；
- 修改文件或模块的影响说明；
- 测试、静态检查、人工验收的命令和结果；
- 风险、迁移、回滚和未验证项；
- GUI 或视觉改动的截图/录屏（注意脱敏）；
- 需要审阅者重点关注的问题。

PR 模板位于 `.github/pull_request_template.md`。写“测试通过”时必须给出测试名称、命令或人工步骤；写“无需测试”时必须解释为什么。

### 6.3 评审和修改

- 代码、行为、数据、构建和安全变更默认至少需要一名非作者审阅者批准；仅文档变更也必须由维护者确认。
- 审阅意见应落到代码、文档、测试或 Issue 决定中，不只在聊天中口头确认。
- 每个未解决的审阅意见在合并前必须得到修改、明确的拒绝理由或维护者决定；解决后在 PR 中说明对应 commit 和验证。
- 审阅期间发现超出原范围的新问题，应新建 Issue，或明确更新范围并得到审阅者同意，不要静默扩大 PR。
- 处理审阅意见后重新运行受影响验证。若修改了提交历史、基线或行为，必须在 PR 评论中说明。

### 6.4 合并与分支清理

满足以下条件才可以合并：范围和验收已完成、必需 CI/检查通过、必需审阅完成、风险和回滚明确、Issue 关联正确。

默认采用 **Rebase and merge**，保留经过整理的原子 commit，便于在 `main` 上定位和回退。只有在确实需要保留分支合并边界时使用 merge commit；只有当提交历史无法合理审阅且 PR 本身已经保留足够证据时，才使用 squash merge，并在 PR 中说明。无论使用哪种方式，都必须通过 PR 合入，不得在本地直接合并后把结果推到 `main`。

合并后：

1. 确认目标分支上的检查和功能结果；
2. 在 Issue 追加关联 PR、合并 commit、验收结果和遗留风险；
3. 更新本地 `.scratch/` spec/议题的状态和评论；
4. 关闭已完成的 Issue；
5. 删除远程和本地已合并分支，保留 PR、commit 和 Issue 记录。

## 7. 调试、回滚和历史追踪

### 7.1 把 Git 历史当作调试信息源

发现问题时，先建立“现象—范围—时间—版本”的对应关系，并收集：

- GitHub Issue 编号、相关 PR 和影响范围；
- 当前版本、最后正常版本和第一个异常版本；
- 相关 commit、配置版本、输入类型和运行环境；
- 最小复现步骤、脱敏日志和测试结果；
- 该问题是否与迁移、外部 API、并发、文件权限或用户数据有关。

若能稳定判定通过/失败，使用 `git bisect` 定位首个异常 commit；每一次判断都要基于同一复现步骤或自动化测试，而不是主观感觉。定位结果回写到 Issue，并通过新 PR 修复。

### 7.2 回滚规则

- 已合入 `main` 的错误改动：新建 `revert/<issue-number>-<short-slug>` 或 `fix/` 分支，使用 `git revert` 生成新的撤销 commit，再走 PR。
- 已推送但尚未合并的分支：优先在该分支提交修复；不要对已被他人使用的分支执行重写历史。
- 仅在本地且尚未共享的临时改动：可使用 `restore`、`reset` 或整理历史，但先确认没有未保存的用户改动。
- 数据迁移、文件移动、视频元数据写入等高风险操作，必须以 Issue 和 PR 中写明的备份/回滚步骤为准；Git 只能恢复代码历史，不能自动恢复磁盘上的原始素材或外部服务数据。

回滚本身也是一个可追踪任务：说明触发原因、撤销的 commit/PR、影响范围、验证结果和后续修复计划。不能用删除 Issue、删除 PR 或强行改写历史代替回滚记录。

## 8. `.scratch/` 与 GitHub Issue 的衔接

现有仓库使用 `.scratch/<feature-slug>/` 保存本地规格和实现议题，这一规则继续有效：

```text
.scratch/<feature-slug>/spec.md
.scratch/<feature-slug>/issues/01-<slug>.md
```

推荐在本地 spec 顶部增加：

```text
GitHub Issue: #123
PR: #456（完成后补充）
Branch: feat/123-short-slug
```

二者职责如下：

- GitHub Issue：任务身份、共享讨论、状态变化、方案决定、PR 关联和关闭总结；
- `.scratch/` spec：完整范围、拆分顺序、依赖、验收矩阵和代理/开发者交接细节；
- `.scratch/` 子议题：可执行的实现单元，保留现有 `Status:` 行和 `## Comments` 追加式记录。

两边出现差异时，先在 GitHub Issue 评论中确认最新决定，再立即同步本地 spec/议题；不能让实现者根据两个相互矛盾的范围继续开发。Issue 关闭前，必须确认本地记录已写入对应 PR、commit、验证和遗留风险。

本地状态可以使用仓库已有的 `claimed`、`resolved` 等执行状态，但它们不替代 GitHub 的五个规范 triage 标签。`needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human` 和 `wontfix` 的含义只能按 [`triage-labels.md`](./triage-labels.md) 使用。

## 9. 从任务到合并的标准清单

### 开发前

- [ ] 已读取相关 `CONTEXT.md`、ADR、Issue 和本地议题。
- [ ] 已说明目标、范围内、范围外、验收、依赖、风险和回滚。
- [ ] 已决定小任务打包方式或大型任务拆分方式。
- [ ] 已创建/更新 GitHub Issue 和 `.scratch/` 记录。
- [ ] 已确认工作区现有修改不会被本任务覆盖。
- [ ] 已从最新 `origin/main` 创建独立分支。

### 开发中

- [ ] 每个 commit 只有一个主要意图，并在安全恢复点提交。
- [ ] 相关测试/检查随实现同步补充，不在最后才一次性猜测。
- [ ] 未提交密钥、运行数据、真实素材或无关修改。
- [ ] Issue 评论记录了范围、方案、阻塞和重要验证。
- [ ] 发现超范围工作时已拆出新 Issue 或取得明确同意。

### 创建 PR 前

- [ ] 分支已同步最新主干，冲突已处理并重新验证。
- [ ] `git diff --check` 通过，工作区没有未说明的改动。
- [ ] PR 正文包含 Issue 链接、范围、验证、风险和回滚。
- [ ] 相关自动化测试、静态检查和人工验收已完成或明确列出未完成项。
- [ ] 文档、ADR、迁移说明和发布说明已按影响范围更新。

### 合并后

- [ ] 只通过 PR 合入 `main`。
- [ ] 已记录合并 commit、验收结果和遗留风险。
- [ ] Issue、本地 spec 和子议题状态已同步。
- [ ] 已删除合并分支，保留 Issue、PR 和 commit 历史。
- [ ] 若出现问题，已用新的修复/回滚分支和 PR 处理。
