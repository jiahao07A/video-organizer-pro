## 四、必须保留的体验改进 Issue

### #16 P0 统一整理方案、批次确认与执行结果

**结论：保留，作为体验主线核心 Issue。**

它要解决当前分析、重命名、物理整理、XMP 和导出入口分散的问题，建立“工作范围 → 整理方案 → 模拟预览与审核 → 批次确认 → 执行 → 结果与恢复边界”的主流程。

它不是单纯的界面改名任务，必须定义素材批次身份、按文件/按操作排除、执行结果统计和恢复边界。依赖 #17、#19，并为 #18、#20 提供批次身份和结果模型。

### #17 P0 显式呈现操作目标集与工作范围

**结论：保留，建议优先于 #16 做目标集原型和共用判定。**

它解决批量动作到底作用于哪些视频素材的问题：有列表选中时使用选中集合，无列表选中时使用当前可见列表全部；工作台不得越过工作范围。它是防止误操作的基础规则，不是可有可无的文案优化。

实现时必须让确认框、执行结果和操作目标集摘要使用同一套判定逻辑，否则会出现界面显示数量与实际处理数量不一致的高风险问题。

### #19 P0 统一写盘副作用与恢复边界

**结论：保留，和 #17 并列为 #16 的前置基础。**

它解决分析、XMP、重命名和物理移动的副作用说明不一致，以及“回滚”容易被用户理解为完全恢复的问题。重点是准确说明哪些动作会写盘、哪些动作可恢复、哪些情况需要人工处理，不是承诺所有操作都能恢复。

自动 XMP、路径差异、冲突、外部修改文件和恢复默认布局都应在小样本和原型中验证。不能只改确认框文案而不记录源路径、目标路径和执行结果。

### #20 P0 增强 AI 结果审阅与来源追溯

**结论：保留，但应在 #16、#22、#21 的共同字段确定后实施。**

它解决用户无法判断 AI 结果来源、标签归一过程和人工修改覆盖风险的问题。需要追踪模型供应商、模型、Prompt 版本、标签库版本、标签来源、过滤原因和强制重新分析差异。

它不应扩展成置信度准确率承诺，也不应恢复已废弃的独立情绪、构图、星级或质量分字段。

### #18 P1 建立任务中心与面向用户的状态体系

**结论：保留，依赖 #16。**

它把分析进度、补跑、重试、取消、整理执行和导出结果从临时反馈变成可回看的任务历史，并区分分析状态、人工状态、文件操作状态和导出状态。

它不应重新设计 ADR-0005 的分析重试规则，也不应把所有长任务强行套用同一套重试模型。#18 适合在 #16 确定素材批次和结果统计后实现。

### #22 P1 重构待审词审核与标准词维护体验

**结论：保留，价值明确，和 #20、#21 有字段依赖。**

它解决待审词来源、出现次数、相关素材、建议动作和处理状态分散的问题，并要求批准到组、挂别名、批量应用 AI 建议和标准词移动都经过明确人工确认。

它不是恢复中转池，也不是增加更多自动扩词能力。标准词必须属于标签组，近义巡检保持次要入口。现有相关 Issue 已有实现基础，但本 Issue 的体验收束仍有价值，不能因为“待审词按钮存在”就关闭。

### #21 P1 增强设置中心的当前生效配置与副作用提示

**结论：保留，价值明确，优先做配置摘要和连接测试。**

它解决用户无法知道实际生效的模型路由、Prompt 版本、标签库版本、自动 XMP、音频转录和批次补跑状态的问题。设置摘要必须和真实路由解析使用同一来源，不能只在 UI 中拼出一份看起来合理的文本。

它不改变 API Key 存储方案，不恢复全局唯一模型，不新增冷启动 AI 分簇路由槽，也不应与 #18 的任务中心合并。

### #23 P1 进行整理方案原型与真实用户走查

**结论：保留，但状态应维持 `ready-for-human`，不能交给代理直接“实现完成”。**

这是验证议题，不是功能开发议题。它依赖 #16–#24 中核心原型或设计稿，需由维护者或产品人员组织至少 5 名目标用户完成脱敏任务走查，验证工作台、素材库、操作目标集、素材预览、模拟预览、整理完成和恢复边界的理解。

它只有在走查证据、用户误解记录和对应议题回写完成后才能关闭。当前不应关闭，也不应把静态产品评审当作用户验收。

### #24 P2 补充新手引导、导出验证与长期工作效率

它包含首次使用向导、环境诊断、FCPX/ALE/XMP 导出验证、连续审片、保存工作集、智能视图和本地历史，价值存在但范围较宽，并且依赖 #16–#22 的核心语义稳定。
