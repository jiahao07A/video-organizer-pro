## 改动与原因

1. **完整指纹和登记**：标准库 `hashlib.file_digest` 替代 4KB Python 读取循环；4 个哈希线程，最多当前批和下一批的任务。64 项一批事务，逐项 savepoint 隔离失败，共用连接减少提交和检查点开销。Windows 等价路径只建一次候选索引，外部连接提交后按 `data_version` 刷新。单条和批量共用持久化规则，仍按输入顺序取得编号，保留最早编号归属及历史成果保护。
2. **缩略图**：实测 OpenCV 的打开全局锁让多个解码线程排队。采用成熟的 PyAV 独立容器解第一帧、单解码线程、缩小后编码，不计算入库无用的 AI base64 和感知哈希；保留 OpenCV 回退、Unicode 路径和视频显示旋转。有效缩略图并发上限 16，避免设置 512 时创建过多解码器。AI 分析的通用抽帧逻辑不受此优化替换。
3. **流水线**：每批登记成功提交并释放锁后才调度缩略图，与下一批完整哈希重叠；等待全部登记完成后再批量落库图片。最终 SQL 按编号、内容版本、路径和非副本条件绑定。重扫缺图的已验证原记录也能补图。
4. **进度界面**：显示总进度及当前阶段两条进度，阶段含发现视频、历史指纹、完整指纹、登记去重、缩略图、完成。未知总数时显示忙碌条和已发现数量；有分母时显示完成数/总数，附耗时、新增、重复、失败统计。Qt 主线程以队列信号更新，在线程启动前连接，避免瞬时任务丢进度；成功和失败均恢复控件。

## 复审与测试真实性

仅沿用两名代理：一名负责登记、一名负责 GUI，主代理负责测量、服务和集成；随后交换只读复审，未扩大代理数量。发现并完成修复：

- 单条登记在哈希后等待数据库锁期间，文件发生变化仍可能把旧指纹标成已验证。现在取得写事务后重新核对；真实锁等待测试验证失败不更改原分析、人工成果、版本、分组和发现历史。
- 重扫已有内容时没有新增记录，旧列表缓存可能仍返回旧摘要和指纹。每批成功登记后失效缓存，真实内容更换测试验证版本和列表同步。
- 缩略图生成及延迟批量绑定期间文件变化。解码前后、结果收集及获得 SQLite 写锁后均重新核实登记快照，变化不绑定；SQL 另外限制版本和路径。

新增测试使用真实临时视频、SQLite、触发器、独立数据库连接、真实线程和 Qt 消息队列。覆盖尾字节变化排除采样哈希、逐项事务回滚、Windows 路径等价、外部写入、预取上限、锁外已提交回调、损坏媒体、重扫缓存、图片方向/颜色/尺寸、源文件完整 SHA256 不变、PyAV 失败的 OpenCV 回退。诊断测试用 Barrier 强制四个不同线程，检查四项异常与 operation/item 的精确对应，没有删减原断言。
