## 证据与结论边界

诊断脚本`.release-build/image400-probe.py`保留在忽略路径，仅输出状态、模型、摘要、尺寸，不输出API Key、Authorization或图片正文；副本配置和原始请求均不进入提交。脚本每次真实请求一条、禁用缓存和自动重试，不做付费并发压测。

已运行：`rtk python .release-build/image400-probe.py --name <本地样本A文件名> --attempts 1 --variant current`，返回与截图相同的HTTP400；`--variant v000`配当前配置、以及`--variant v000 --profile old`配旧版配置，均复现相同400。后续一次当前请求还遇到HTTP520，属于不同服务端错误，不作为unsafe根因或成功证据。

同配置的正文127495字节，SHA-256为`cfd8b1da38f183a9cba9b1b37a860ec432554b804381fbeccab72a000538db82`。旧版自身配置的提示词略有差别（正文127504字节），但8帧摘要仍相同、路由身份相同，也返回400。用户报告的32/64与随后磁盘设置32/128不同，不能将当前磁盘快照倒推为失败当时配置；单请求复现已排除高并发是必要触发条件。

目前未找到新版图片/请求构造回归；可确认服务端对该输入给出拒绝，但具体规则、审核原因或后端节点仍未知，不能仅凭unsafe推断素材损坏或画面违规。服务端未返回x-request-id/x-trace-id，需结合本地请求时间、实际供应商/模型和请求摘要进一步定位。

可证实的程序遗漏是错误提示仅匹配`image_url`，未匹配`image_url.url`，导致仍显示英文异常字典。此次提示修复不能表述为消除了服务端400。
