# 更新退出交接：规范轴复审

## 范围与结论

以 RC12 基线 `0716dda` 为参照，复核本轮主窗口退出、素材监控停止、备份恢复与监控重配置的异常边界及其新增测试。最终检查包含主审已提交的 `a85aa7d` 补正。两轮发现均已按主审执行包补正；当前差异中未发现仍未解决、可明确复现且由本轮引入的问题。

检查遵循仓库 Git 工作流与领域约束：不改变普通关闭到托盘语义，不强杀线程或进程，不提前释放安装互斥，不以测试覆盖用户现场数据；仅在退出被接受且监控停止成功后请求退出 Qt 事件循环。失败路径明确拒绝关闭并允许后续重试。

## 第一轮：持续停止失败导致重试退出隐藏主窗

问题为 P2。更新退出首次停止监控失败后，FAILED 恢复清除了更新退出状态；用户再点击托盘“彻底退出”会进入未保护的普通关闭分支。停止持续抛错时，异常从 Qt 回调漏出，主窗隐藏而事件循环仍存活。

先红：新增 `persistent_monitor_error` 场景后单独运行得到 `1 failed, 7 deselected`。真实托盘 QAction 触发后出现 `closeEvent` 异常，并命中“持续停止失败后不能隐藏窗口”断言，子进程看门狗退出码为 23。证据目录：`.release-build/update-exit-persistent-agent-a-red`。

补正：提取 `_stop_monitor_for_exit`，更新退出和普通真正退出共同调用；异常时 `event.ignore()`，清除退出接受及允许标志，显示主窗。更新阶段通过 controller FAILED 解冻，后续普通重试失败则再次提示取消安装器后重试。

后绿：`tests/test_update_exit.py` 为 `8 passed in 10.00s`，证据目录：`.release-build/update-exit-persistent-agent-a`。新增场景验证持续失败后窗口可见且中心区可用、不触发 quit、再次提示，并通过 QTest 点击主题按钮确认交互；仅在明确恢复停止方法后再次触发真实托盘退出并成功结束线程与事件循环。

## 第二轮：TimeoutError 调用契约未覆盖维护入口

问题为 P2。监控停止增加超时显式失败后抛出 `TimeoutError`；它不属于 `RuntimeError`。备份与恢复原先只捕获后者，监控重配置槽也未捕获超时，导致错误漏出 Qt 回调而没有面向用户的恢复提示。

先红：新增 `tests/test_monitor_stop_gui_recovery.py`，使用实际 `MediaDirectoryMonitor`、真实 Thread/Event 和 0.02 秒停止等待。备份、恢复、重配置三个场景均从实际 stop 抛出超时，结果为 `3 failed in 0.92s`。证据目录：`.release-build/monitor-stop-gui-agent-red`。

补正：备份与恢复入口捕获 `(RuntimeError, TimeoutError)`，沿用警告与禁止数据操作的行为；重配置槽仅捕获 `TimeoutError`，提示旧监控仍在停止、设置已保留、稍后再次保存重试。未修改监控配置提交顺序，也未自动启动仍在停止的线程。

后绿：新三项、停止超时三项与更新退出八项联合为 `14 passed in 10.79s`；证据目录：`.release-build/monitor-stop-gui-agent-green`。测试验证失败时不调用备份/恢复数据操作、不覆盖监控原配置；释放并等待真实线程结束后再次操作成功。测试 finally 释放自己的线程并关闭分析池。`git diff --check` 通过。

## 最终只读检查

- `core/media_watch.py`：停止监控线程或 Observer 超时后显式失败；在确认退出前不销毁分析池，后续 stop 可重试；保留原 `wait=False` 行为。
- `gui/main_window.py`：两个真实关闭分支共同使用保护边界；停止失败不会置接受关闭标志，更新失败清除冻结标志并解冻中心区与更新通知；普通关闭到托盘分支保持原行为。重配置超时保留旧监控配置与已保存的新设置，并明确要求重试。
- `gui/views/settings.py`：两种维护操作在监控停止超时后均提前返回，不进入备份/恢复数据操作。
- 新增测试：持续失败场景实际触发托盘 QAction，维护恢复测试使用真实阻塞线程而非仅返回预设异常；等待、看门狗和清理均有界，不以产品强制退出掩盖失败。

本轮最终复查只读，未再运行大型测试。主审的最终全量测试、冻结包安装更新闭环与发布回验应以最后产品提交后的证据为准，不能使用补正前的全量结果替代。

## 未验证边界

本规范轴复审没有 Windows 10 实机环境，不能据此宣称 Windows 10 全功能已实测。源码子进程 probe 替换安装预检与安装器启动，不能单独证明真实安装器、AppMutex 与旧进程交接时序；由主审的隔离冻结包闭环补足。当前机器上的 Windows 原生四场景结果由主审独立掌握，不作为本代理重新执行的结果。

join 超时采用真实受控阻塞线程，未穷举 Windows 文件系统驱动、远程盘或 watchdog 系统 API 永久阻塞。分析池 shutdown 的等待策略为既有行为，本轮未证明任意第三方分析调用永久挂起时都能退出。`aboutToQuit` 清理属于应用已经开始退出后的兜底，不能作为可拒绝退出的恢复边界；本轮正常更新/托盘退出在它之前通过主窗保护路径完成停止。

已运行 RC10 的旧程序不会因重新发布 RC12 获得源码补正；现场旧进程处置和同版本覆盖安装说明仍需由主审交付。复审未操作用户现场进程、素材、数据库或配置。

## 导出测试等待与隔离补正

发布前全量出现导出测试通知超时，并让晚到 JSON 成功回调污染下一项 FCPX 测试。新短路径 `.release-build/cli-d1` 单独运行 JSON 用例仍失败，结果 `1 failed in 7.24s`，排除必须依赖长路径、全量测试或编译并发的解释。

忽略目录中的诊断探针记录：原 QTest.qWait 轮询下，导出在 1.149 秒进入、5.661 秒返回，耗时约 4.512 秒；4 秒线程栈显示后台线程在 media_registry.register 的 SQLite 事务退出路径，主线程在 qWait 轮询。仅给轮询增加 `time.sleep(.001)`、保留原业务超时后，导出耗时约 0.246 秒，任务及 finished 信号随即送达。该证据支持等待循环造成后台 Python 线程调度饥饿，不支持业务导出死锁。

按主审批准，仅在 `tests/test_review_cli_result_exports.py` 的异步轮询中主动释放 GIL。JSON 等待维持 5000 毫秒；FCPX 原 150 次 20 毫秒轮询改为明确的 3000 毫秒期限，未放宽断言。finally 增加最多 5000 毫秒等待真实 `_io_worker` 及 queued 清理回调、确认引用清空，再关闭和 deferred-delete 视图，避免跨测试回调污染。未改产品导出或 Worker 实现。

最终整文件复验：新目录 `.release-build/cli-d6`，`12 passed, 1 warning in 7.76s`。警告为既有 `invalidateFilter()` 弃用提示，未影响结果。
