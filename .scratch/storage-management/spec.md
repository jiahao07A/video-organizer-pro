## 1. 问题陈述

用户希望素材库日常保存与查询不因总库存增长而明显变慢，同时消除启动阶段重复升级迁移的等待，并确保管理数据可以安全备份、恢复和整体搬迁。

静态检查发现：旧结果 JSON 只要存在就会在每次服务初始化时逐条写入数据库，每条单独提交；主窗口此时尚未显示。分析收尾加载全库并重写 JSON/CSV，单条元数据编辑也先读取全库。设置同时保存到文件与数据库，数据库整包会覆盖文件同名项；标签词表同样存在配置文件与数据库双份数据。数据库备份直接复制主文件，没有明确的运行中一致性与受控恢复协议。

这些是需要测试覆盖的代码路径，不是实测耗时或已验证的数据损坏结论。此前 GUI 合成数据基准不包含模块导入时间，也不覆盖旧 JSON 首次导入，不能证明进程级普通启动满足本轮目标。

## 2. 用户结果

- 数据实时保存到明确的权威来源；JSON/CSV 结果文件改为按需导出，不再是启动时自动回灌的第二份素材库。
- 首次升级先提示并备份，显示进度；相关管理数据操作在升级完成前不可用，窗口仍能响应。成功后记录完成状态，普通启动不重复升级。
- 已有有效数据库时，以数据库中的素材记录为准，不自动合并旧结果 JSON。旧 JSON 可以保留为人工导入来源，但没有隐式覆盖或补回取消入库记录的行为。
- 默认程序旁的 `data/` 作为统一数据目录，支持自选；不可写时提示另选，不静默切换位置或新建空库冒充成功。
- 管理数据目录可以整体搬迁；原始视频仍保留原位置，跨电脑原始视频路径重定位不属于本轮。
- 单条保存、批量操作与分析收尾避免全库处理；备份和恢复具有明确校验、保护与失败恢复行为。
- 当前 Windows 设备上，以 50,000 与 200,000 条合成记录验证：普通启动从进程启动到主窗口可操作且首批结果可见的 p95 目标不超过 2 秒。首次升级单独计时。

## 4. 实现决定与约束

### 4.1 每类数据只有一个权威持久来源

采用按数据类型单一来源，保留现有 SQLite 与配置文件形式，不以“统一目录”为由把所有数据重写成新格式：

- 素材记录、入库编号、标准词、别名、待审词、历史记录：SQLite。
- 用户设置：统一数据目录内的设置文件；数据库内历史设置副本只在明确升级/恢复时读取，普通运行不再覆盖文件。
- 标签组定义、组规则、提示词与导出规则：统一数据目录内的标签配置文件；其中标准词列表属于从 SQLite 生成的兼容投影，不再独立编辑或自动回灌。
- 缩略图：数据目录内的可重建文件，不是分析结果或素材库主数据。
- JSON/CSV 分析结果：显式导出文件，不是缓存恢复源或自动同步副本。
- 备份：有来源、版本、完成状态与校验信息的恢复产物，不参与普通启动取数。

首次切换设置来源时，保存升级前按旧优先级实际生效的完整配置，之后停用双份覆盖；不得仅选择旧设置文件而丢弃数据库中更新的路由、密钥或偏好。旧标签配置与标准词表的差异应列入升级报告，冲突以数据库中的标准词为准，不静默新增、删词或改组；配置独有词保留在源快照与差异报告，必要时由用户显式导入并确认归组。

配置文件采用同目录临时文件与原子替换；持久化失败不显示已保存，也不让界面/运行时把未保存值当作成功状态。涉及配置与数据库的组合变更必须有可恢复的提交协议，不承诺不存在的跨文件原子事务。

### 4.2 启动协调与一次性升级

启动协调入口负责定位数据、读取轻量版本信息、决定普通打开/提示升级/报告问题，再创建可用服务。低层文件管理器构造不能触发无条件导入。

- 以持久版本和完成记录判断是否需要升级，普通启动不扫描全库、重复执行已完成的结构变更或读取全量结果 JSON。
- 新建库直接创建当前结构；旧库结构变化按版本执行。异常不能被“字段已存在”类宽泛捕获静默吞掉。
- 检测源数据与展示迁移计划发生在目标空库创建之前，避免新建空库掩盖旧库的存在。
- 已有有效数据库时，不自动合并旧结果 JSON；没有可用旧数据库且有旧 JSON 时，经确认后作为首次导入源。损坏的数据库属于错误，不能静默降级为仅 JSON 或空库。
- 检查、备份、批次转换、验证、激活与完成记录组成可恢复流程；仅验证和启用成功后记完成。
- 批量导入使用受控事务与有界内存；重复项、无效行和失败原因有脱敏报告。保证已有入库编号不被重新分配。
- 取消开始确认不写目标主数据；执行中断保留原数据和未完成状态，重启提供恢复/重试，不放行半完成数据。
- 升级期间相关数据操作暂停，窗口可响应；普通启动不会为历史迁移重新付出完整数据校验成本。
- 遇到高于当前程序可理解的数据版本，明确拒绝写入，不尝试降级。

### 4.3 统一数据目录

开发环境以项目位置、打包环境以可执行文件位置确定默认程序旁的 `data/`，不使用进程工作目录。支持一个持久的用户自选位置；用于定位该位置的启动记录只保存路径/版本等必要信息，不复制业务设置或密钥。

目录切换走现有升级/恢复协议，包含数据库、配置、缩略图与既有备份。目标若已有有效数据，必须明确选择打开已有目录或搬迁当前目录，禁止隐式合并/覆盖。复制目标及所有引用验证成功后才激活，保留源目录供人工后续清理。数据目录内部资源使用相对数据根的引用；原始视频路径不因此改变。无法定位原始视频时如实显示缺失，不能自动取消入库。

本轮不设计多库切换产品、不移动原始视频、不自动猜测其他电脑的新素材路径；用户自选数据目录与便携默认位置都应在设置界面可见。

### 4.4 日常素材读写与导出

继续使用现有服务接口作为主要测试与 GUI 接入边界，保留已经实现的 SQL 分页/筛选。

- 单条详情读取与编辑按稳定标识/路径访问相关记录，只更新允许编辑的字段，避免全库读取和用过期整行覆盖后台新结果。
- 批量入库、取消入库和相关写入使用有界事务；多批处理中断时正确报告已提交部分，不把整批误报为成功。
- 分析的成功结果仍逐条可靠落库；降低连接/提交成本不得把整个分析任务结束前的成功结果留在易丢失内存中。
- 分析结束不隐式读取全库、生成全量内存缓存或重写全库 JSON/CSV；重命名收尾等同类隐式结果输出一并检查。
- 详情/查询缓存有界并在写入、取消入库、恢复或目录切换时更新/失效，不能以完整全库缓存作为默认操作前提。
- 显式导出按操作目标集执行；全库导出须明确选择。按批读取并流式输出，在同目录暂存并成功后替换目标文件；取消/失败保留已有文件并报告原因。
- 保持工作范围、可见列表、操作目标集及强制重新分析的既有语义；不得为了性能扩大批量操作范围。

### 4.5 备份与恢复

数据库使用 SQLite 支持的一致性快照，不直接复制运行中的主数据库文件或依赖碰巧已完成 WAL 检查点。WAL 是 SQLite 的预写日志，已提交内容可能仍在该日志中。

快照与配套配置在受控写入边界内捕获，记录版本、必要文件、完成状态与校验；资源密钥仍属本机敏感数据，备份不能进入 Git、Issue、PR 或公开输出。备份不包含原始视频；缩略图与缓存缺失可重建，不得阻止核心数据恢复。

恢复须验证备份、拒绝不支持的版本、暂停冲突任务并关闭旧连接。先保护当前数据，再在暂存位置验证待恢复数据，成功后启用并刷新服务/缓存，或明确重启生效。恢复失败不能留下混合版本的库与配置，也不能报告成功。

## 5. 验收与测试决定

### 5.1 测试边界

用户已认可两个测试入口：现有素材/设置/标签服务接口，及新增的启动协调入口。以保存、重启、查询、导出、备份、恢复后的可观察结果为断言，不要求某张内部表或某条 SQL 的具体实现。为性能不退化可通过查询观测断言单条保存/分析收尾没有全库读取，避免仅用脆弱的函数调用次数冒充用户验收。

已有素材库查询、设置持久化、工作范围、视频缓存与分析管线测试可作为回归参照。每个任务按测试先行完成自己的正常/失败路径，不把正确性留到最终验收才补。

### 5.2 必须覆盖的场景

- 旧数据库与旧 JSON 同时存在，JSON 内容过期、缺字段或包含已取消入库记录。
- 只有旧 JSON、只有旧数据库、全新目录、损坏数据库、损坏 JSON、未知新版本。
- 迁移确认取消、转换中断、备份失败、写盘失败、激活失败、完成记录失败与重复启动。
- 设置副本冲突、标签投影冲突、保存失败后界面状态、关闭再启动与服务缓存失效。
- WAL 中存在已提交记录，备份与当前写入竞争，损坏/缺件/不支持版本的恢复。
- 两种规模下的单条详情保存、批量入库/取消入库、分析收尾及显式导出。
- 不同工作目录启动、不可写默认目录、自选目录、目标已有库、整体搬迁后的缩略图与稳定入库编号。
- 分析中成功落库后取消、重启不丢成功结果；操作目标集边界和原始视频不被数据管理操作改变。

所有自动化测试在临时目录使用合成数据与测试密钥，不打开生产数据库、真实设置或私人素材。

### 5.3 性能口径

- 在当前 Windows 设备记录 CPU、内存、磁盘类型、系统、Python/依赖与源码/打包模式，使用同一设备、同一生成器与相同负载比较基线版本和实现版本。
- 每个规模至少重复 20 次，记录全部样本、中位数、p95 与峰值内存。首次进程启动与后续进程启动分别展示，不把文件系统冷缓存和模块首次导入混称为同一种冷启动。
- 计时起点为父进程发起应用启动；终点为 UI 事件循环已响应、主窗口可操作且首批结果完成呈现。包括模块导入、初始化、数据定位和首批查询，不以空窗口出现代替完成。
- 50,000、200,000 条记录的普通启动 p95 各自目标 ≤ 2,000 毫秒。工作台按现有产品语义恢复或为空；测量必须包含素材库首批记录，不能利用默认空工作范围跳过数据就绪。允许由基准在主窗口就绪后进入素材库并等待首批，仍连续计入同一耗时。
- 首次升级迁移独立报告备份/转换/验证时间与峰值内存；用户确认等待不计入处理性能。记住范围引发的媒体扫盘在后台单独计时，不拖延基本交互就绪。
- 日常读写记录相同输入下的延迟、提交次数/数据访问范围、内存与 UI 响应。不得承诺未经讨论或测量的单条保存毫秒数；不得用 AI 网络耗时、媒体解码或全库显式导出掩盖存储路径表现。
- 首个实现任务动手前固定合成输入和原版基线；最终任务复用相同口径，未达标如实报告并定位，不删除校验、减少测试数据或修改计时起止制造通过。

## 6. 实现任务与依赖

本地每项独立记录在 `issues/` 下，并与 GitHub 子议题双向关联。用户已确认以下拆分与依赖：

1. 可靠备份与受控恢复：无前置。
2. 一次性升级迁移：依赖 01。
3. 统一便携数据目录：依赖 02。
4. 设置与标签存储一致性：依赖 03。
5. 素材按需读写与显式导出：依赖 03。
6. 完整性能与恢复验收：依赖 04、05。

实现入口是 01。每项从最新已集成的前置成果创建独立分支并经 PR 合入；04 与 05 仅在 03 完成后可以分别开展。文档 PR 合并不表示这些任务已经完成，也不自动关闭父议题。

## 7. 范围外

- 云同步、服务化、换数据库、换桌面框架。
- 原始视频移动、跨电脑原始视频路径重定位、多库切换产品。
- 自动缓存清理、自动备份轮转、磁盘空间治理。
- AI 网关/模型路由语义、标签人工确认规则、分析重试及进度规则改写。
- 批次物理整理、重命名事务与完整素材回滚系统重建。
- 新密钥管理产品或自动上传备份。

## 8. 风险、回滚与交付边界

迁移、目录切换和恢复都可能损坏真实管理数据，必须在验证快照可恢复后执行。保留源数据，不以删除旧文件作为优化手段；代码撤销不能自动恢复数据库或配置。涉及数据版本提升时记录旧程序能否直接打开，不能承诺用旧代码打开升级库等于数据回退。

最终交付须包含升级说明、操作指引、性能样本与故障恢复证据；更新相关 README/维护文档时继续使用 `CONTEXT.md` 的领域术语。任何目标无法达到或必须扩大范围的发现，都先更新父/子议题与规格并确认，不静默引入新架构。
