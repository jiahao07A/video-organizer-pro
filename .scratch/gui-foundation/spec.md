# Spec: GUI 根本重构——大素材库性能、设置与标签管理

Status: needs-info  
Created: 2026-10-05  
Feature-slug: `gui-foundation`  
Domain: `CONTEXT.md`；架构决策见 `docs/adr/`

## 问题陈述

当前反馈集中在三个相互关联的问题：设置项难找；标签审核与词库操作需要更顺畅的搜索和批量流程；当素材量增大、筛选或后台任务进行时，GUI 响应明显变差。目标规模为 50,000–200,000 条视频素材。产品仍须作为单个本地 Windows 桌面应用运行。

这不是单纯换配色或把桌面控件搬进网页的问题。必须先修正数据装载、筛选、缩略图更新和后台工作与 UI 的边界，再根据相同负载下的实测结果决定是否换前端技术。

## 本轮已确认

- 性能目标：首屏与首批素材快速可见；筛选、排序、滚动与缩略图加载保持顺畅；扫盘、分析、导出期间界面持续可交互；长时间使用的内存占用可控。
- 初始性能验收建议：主窗口可操作且首批结果可见不超过 2 秒；常用搜索、筛选、排序不超过 300 毫秒。须在目标 Windows 设备与 50,000、200,000 条测试数据上记录中位数及高分位耗时后定版。
- 设置：可搜索的设置目录；普通偏好保存后立即生效；敏感配置须有清晰的保存/确认反馈。
- 标签：待审审核是首要路径；待审结果应支持逐条审阅和多选后应用所选 AI 建议；标签标准词预计少于 500 个。
- 标签库允许重新设计，不再要求永久维持“左待审面板 + 右侧标签组栏”这一具体布局。工作视图可以分别服务待审审核和标准词管理。
- 部署：一个本地 Windows 桌面应用；不要求用户单独启动服务或手动打开浏览器。
- 技术方向：暂不决定保留 PySide6、改用嵌入式 Web 前端或评估 Windows 原生前端；Python 业务逻辑和本地数据当前均应作为可复用资产考虑。

## 当前实现证据与待验证假设

当前应用基于 PySide6，业务与数据代码主要位于 `core/`，GUI 位于 `gui/`。以下代码路径值得优先测量，但静态检查不能代替运行时 profiling：

1. `DatabaseManager.get_all_videos()` 使用 `SELECT * FROM videos ORDER BY timestamp DESC`，素材库加载会把全量记录交给 GUI。
2. `AdvancedSortFilterProxyModel.filterAcceptsRow()` 对模型中的每行调用 Python 筛选函数；搜索与高级筛选的耗时可能随素材量线性增长。
3. `VideoTableModel.on_thumbnail_loaded()` 每收到一张缩略图，会遍历当前模型中的所有素材来定位对应行；高数据量下可能造成重复全表扫描。
4. `MainWindow.setup_ui()` 在启动阶段创建工作台、素材库、标签库和设置页；首次显示成本需要单独量测。
5. 标签待审队列目前是单选列表，AI 批量分拣通过另一弹窗完成；标准词管理与待审处理需要进一步验证搜索、选择和批量操作的连贯性。

以上是可检验的候选原因，不预先断定 Qt 本身是根因。

## 目标

### 性能与数据路径

- 全库不再作为 GUI 的默认装载单位；优先从数据库按需筛选、排序、分页/分段取数，并仅读取列表需要的列。
- 首次渲染只请求首批和当前视口需要的数据；滚动时增量加载，不要求预先生成所有控件或缩略图。
- 数据库查询、目录扫描、缩略图解码和其他可能耗时的工作不得阻塞 UI 线程；所有 UI 状态更新仍须回到 UI 线程。
- 筛选条件与排序应尽量在 SQL/服务层执行，避免每次键入都对几十万条 Python 对象做完整重滤；保留“列表选中优先，否则当前可见列表”的操作目标集语义。
- 缩略图加载按可见区域与优先级调度，采用稳定的路径到行映射和有界缓存；不因一张图完成而遍历全库。
- 页面按需创建或初始化。页面切换可刷新数据，但不得导致无关页重复执行全量读取。
- 先记录启动耗时、首次可见结果时间、筛选/排序延迟、滚动与缩略图行为、UI 线程最长阻塞时间和峰值内存。

### 设置界面

- 提供设置搜索和清晰的分类导航；分类按用户任务组织，而不按内部配置文件或模块名组织。
- 普通偏好保存后立即生效，并显示已保存/失败状态；API Key 等敏感字段须有清楚的确认或保存反馈，不能让用户误以为修改已生效。
- 把低频高级选项与日常设置分层；帮助文案解释“改动影响什么、何时生效”，避免把所有选择都放在一个长表单里。
- AI 供应商、任务模型路由、提示词、分析性能/重试、界面和导出配置分别有明确入口；不改变现有领域行为。

### 标签管理

在同一“标签库”中提供围绕两类工作的清晰工作视图：

1. **待审审核**：可搜索、筛选、排序待审词；显示原文、来源和可用的 AI 建议；多选后“应用所选”仅执行用户明确选中的建议。批准、挂别名或丢弃仍须遵守人工确认边界，禁止静默写入。
2. **标准词管理**：可搜索和按标签组筛选标准词；清楚区分标准词与别名；支持快速编辑、标签移动和有约束的批量操作。近义巡检、标签使用统计等低频能力不抢占主工作区。

采用列表、表格、分栏或其他控件形态，应通过原型与真实操作任务验收。标准词须始终归属标签组；待审词不是标准词；标签归一和人工确认规则不变。低于 500 个标准词时，不能仅以“标签数量很大”为由引入复杂的虚拟化交互。

## 技术路线比较

### A. 重构 PySide6 前端（首选第一阶段基线）

优点：沿用现有 Python、本地 SQLite、PyInstaller 部署与 Windows 桌面集成；业务与数据逻辑改动可与 UI 重设计分开；迁移和安装风险最低。  
风险：需要验证复杂交互原型的开发效率和高数据量下控件/模型的体验；仍须重做数据访问与列表模型，单换控件不会解决全量查询。

### B. 单个桌面包内嵌本地 Web 前端

Python 继续承担业务与数据访问，Web UI 通过桌面壳/WebView2 与本机进程通信；最终仍交付单个本地桌面应用，不要求用户操作浏览器或手动启停服务。  
优点：复杂表格、搜索、筛选与现代设置界面有较丰富的前端组件和样式工具。  
风险：新增 JavaScript/TypeScript 构建链、WebView2 运行时/桌面壳与 Python 进程生命周期、前后端通信和本地访问安全；不能自动改善数据库的全量查询、过滤或线程阻塞。

### C. Windows 原生前端

例如以 C#/.NET 实现 Windows UI，并将既有 Python 业务保留为本地进程/API 或逐步迁移。  
优点：Windows 原生集成与系统控件一致性。  
风险：需要第二套语言/构建链与更复杂的进程边界；若没有明确的 Windows 原生能力需求和长期维护资源，重写成本高于本轮可证明的收益。

### 建议

先在现有 PySide6 实现与上述路线无关的数据层修正和 profiling；同时用可复用的标签管理/设置原型验证 UX。只有当修正后的 PySide6 在目标数据规模或交互迭代速度上仍达不到验收要求时，再做 B 路线的小型打包原型对照。C 暂不作为首选，除非之后出现必须依赖 Windows 原生 API 的明确需求。

Web 对照原型须在同一台 Windows 机器、同一数据库规模、同一筛选/滚动/后台任务下比较；同时记录冷启动、首屏、交互延迟、内存、打包体积、开发迭代成本和文件/媒体能力。不得仅凭静态观感决定迁移。

## 分阶段交付

1. **性能基线**：针对 50,000 与 200,000 条记录，生成不含私人素材的可重复测试库；记录当前指标和目标硬件。
2. **高数据量数据路径**：验证 SQL 筛选/排序、分段读取、轻量列投影、按需缩略图及增量更新；保持操作目标集与工作范围边界。
3. **设置与标签交互原型**：至少覆盖设置搜索与即时保存反馈、待审批量 AI 审阅、标准词搜索/移动/批量维护；通过代表性任务走查后锁定布局。
4. **PySide6 实现与验收**：将性能基线与交互原型落到现有单一桌面应用，检查自动测试和人工 GUI 验收。
5. **技术路线复核**：若阶段 2–4 后仍不满足性能或 UX 目标，再实现有限 WebView2 打包原型；只有对照证明收益足以抵消长期维护/打包成本，才提出前端迁移 ADR。

## 验收标准

- 目标 Windows 设备上，以 50,000 和 200,000 条测试记录测量：主窗口可操作且首批数据可见 ≤ 2 秒；常用搜索、筛选、排序 ≤ 300 毫秒（最终口径应明确计时起止与分位数）。
- 扫盘、分析、导出期间，主窗口可持续响应；无全量表重复加载或缩略图完成后扫描所有素材的退化路径。
- 长时间滚动与反复筛选后内存占用有界，列表与详情数据一致。
- 设置可通过搜索或分类导航找到；普通偏好保存后能看到明确的生效/保存结果；敏感项提示保存状态。
- 待审词可搜索、多选并只应用明确选中的 AI 建议；未确认的建议不会写入标签库。
- 标准词可快速搜索、按组筛选、编辑和移动；标签库日常流程不依赖弹出多个互不衔接的窗口完成。
- 最终分发仍为用户可直接启动的本地 Windows 桌面应用，不要求用户单独启动服务或手动访问浏览器。

## 暂不包含

- 不重写 AI 分析、标签归一、导出与工作范围的领域规则。
- 不迁移到云服务或将视频/数据库上传到外部系统。
- 在 profiling 前不把 Qt 认定为唯一性能根因。
- 在对照原型证明收益前不全量迁移到 Web 或 .NET。

## 待确认

- 性能数字应在哪一台/哪类 Windows 设备上作为硬验收门槛；当前 2 秒与 300 毫秒为建议初值。
- 是否开展嵌入式 Web 原型，以及是否有可持续维护第二套前端工具链的资源。
- 标签工作视图的最终信息架构和待审 AI 建议的行内呈现方式，应由原型走查确认。
